# Plan — UI Tools for Copilot

**Status:** proposed · §11 records the WebMCP discovery mechanism, validated 2026-09-03 · **Date:** 2026-09-03 · **Scope:** `com.etendoerp.copilot` only
**Prerequisite reading:** [../request-flow.md](../request-flow.md), [../tools-system.md](../tools-system.md)

## 1. Goal

Let the LLM act **on the user's screen**, not only on the server.

Two capabilities in v1:

| Capability | What it does |
|---|---|
| `ui.navigate_window` | Opens an Etendo Classic window/tab (optionally on a record) in the host application |
| `ui.draw_svg` | Renders an SVG inside the chat bubble |

And, more importantly, the **generic mechanism** behind them: any host UI declares what
it can do, those capabilities become LLM tools for that request only, and when the LLM
calls one the action travels back down the chain and is executed in the browser.

> Different UIs send different capabilities. A Classic-embedded chat offers navigation; a
> dashboard widget may offer only `ui.draw_svg`; a future stand-alone UI may offer
> something else entirely. The assistant configuration does not change — the *request*
> does.

## 2. Why this is cheap to build

From [../request-flow.md](../request-flow.md):

- `extra_info` is an untyped dict that crosses Java→Python untouched and is already
  available to every tool through `ThreadContext.get_data("extra_info")`. **Forward
  channel: free.**
- `RestServiceUtil.serverSideEvents` relays every `data:` line **verbatim**, so a new SSE
  `role` reaches the browser with zero Java changes. **Return channel: free.**
- `ToolLoader.get_all_tools()` already synthesises tools at request time from request
  data (OpenAPI specs, MCP servers). **Dynamic tools: an established pattern.**
- The chat iframe is **same-origin** with the Classic page, so
  `window.parent.OB.Utilities.openDirectTab(...)` is directly callable
  (confirmed at `modules_core/org.openbravo.client.application/web/…/ob-utilities.js:367`).

Two things are *not* free and drive the phasing: the streaming request is a GET with a
4-parameter whitelist (§4.1), and rendering SVG safely needs a sanitiser (§7).

## 3. Architecture

```
   Browser (chat iframe)                Java                    Python                LLM
 ┌──────────────────────┐        ┌────────────────┐      ┌──────────────────┐
 │ capability manifest  │───(1)──▶ UIToolsHook    │──(2)─▶ extra_info.ui    │
 │ + ui context         │        │ validates vs   │      │        ↓         │
 │                      │        │ ETCOP_APP_TOOL │      │ UIToolFactory    │──(3)──▶ tools
 │                      │        └────────────────┘      │ builds synthetic │
 │                      │                                │ tools            │
 │                      │                                │        ↓         │◀──(4)── tool_call
 │ UIActionDispatcher   │◀──(6)── verbatim SSE relay ◀─(5)─ __ui_action__   │
 │  ├ navigate handler  │                                │ envelope         │
 │  └ svg handler       │                                └──────────────────┘
 └──────────────────────┘
```

1. UI declares `capabilities` + `context` on each question.
2. A `CopilotQuestionHook` validates them against what the assistant is allowed to use and
   writes `extra_info.ui`.
3. Python turns each surviving capability into a `StructuredTool` bound to the LLM.
4. The LLM calls it like any other tool.
5. The tool does **no work**; it returns a marker envelope, which the streaming layer
   converts into an SSE line with `role: "ui_action"`.
6. The chat dispatches it to a client-side handler.

### 3.1 The two-key rule

A UI tool is offered to the LLM only if **both** are true:

- the **administrator** enabled it for this assistant (`ETCOP_APP_TOOL` row pointing at an
  `ETCOP_TOOL` marked as a UI tool), and
- the **client** declared it in this request's capability manifest.

Neither side alone can widen the surface. An old chat build talking to a new assistant
simply gets fewer tools; a rogue client cannot invent a capability the administrator never
granted.

## 4. Wire contracts

### 4.1 Forward: browser → Java

Two new request parameters, both optional:

| Param | Shape | Size |
|---|---|---|
| `ui_capabilities` | comma-separated ids, e.g. `ui.navigate_window,ui.draw_svg` | tens of bytes |
| `ui_context` | JSON object, see below | **hard cap 4 KB** in v1 |

```jsonc
// ui_context
{
  "host": "etendo-classic",       // "etendo-classic" | "widget" | …
  "protocol": "1.0",
  "window":  { "id": "…", "tabId": "…", "title": "Sales Order" },
  "mode":    "grid",              // "grid" | "form" | "new"
  "selection": [ { "id": "…", "identifier": "1000123" } ]   // max 20 entries
}
```

**Only ids and identifiers travel here — not full records.** Full record content stays in
the existing `<Context>` block until §9 replaces it; the point of `ui_context` is *where
the user is*, not *what the data says*.

Java changes:

- `RequestUtils.retrieveParametersAsJson` — add `ui_capabilities` and `ui_context` to the
  whitelist (`RequestUtils.java:33`). This is the reason the cap exists: on the streaming
  path these ride the query string.
- A capability list longer than the cap, or a malformed `ui_context`, is **dropped with a
  log line** — never fatal to the question.

### 4.2 Java → Python

`UIToolsHook` (new `CopilotQuestionHook`, priority 50) writes:

```jsonc
"extra_info": {
  "auth": { … }, "model_config": { … },
  "ui": {
    "protocol": "1.0",
    "host": "etendo-classic",
    "capabilities": ["ui.navigate_window", "ui.draw_svg"],   // already intersected
    "context": { …ui_context minus capabilities… }
  }
}
```

### 4.3 Tool → stream (the action envelope)

A UI tool's return value is a JSON string:

```json
{"__ui_action__": {
   "v": 1,
   "id": "b3f1…",
   "tool": "ui.navigate_window",
   "args": { "windowId": "181", "tabId": "186", "recordId": "1000123", "mode": "form" },
   "say": "Opening the Sales Order 1000123."
}}
```

- `id` — idempotency key, so a replayed stream does not navigate twice.
- `say` — what the LLM wants the user to read; also what the tool returns to the model as
  its observation, so the conversation reads naturally.

### 4.4 Python → browser (SSE)

```
data: {"answer":{"role":"ui_action","conversation_id":"…","response":"{\"v\":1,\"id\":…}"}}
```

`response` stays a **string** so that nothing in the existing Java or UI plumbing has to
change its type. Java relays it verbatim.

For the synchronous endpoints the same actions are accumulated and returned as
`answer.metadata.ui_actions: [ … ]`, which `extractResponse` already copies to the client
(`RestServiceUtil.java:658`). ⚠ fix issue **B4** first or metadata is dropped on one branch.

### 4.5 Capability registry (single source of truth)

`copilot/core/ui_tools/registry.py`:

```python
UI_TOOLS = {
  "ui.navigate_window": UIToolSpec(
      name="ui.navigate_window",
      description=("Open a window in the user's Etendo screen. Use it when the user asks "
                   "to go to / open / show a window or a specific record. "
                   "This does not read or modify data."),
      args_schema=NavigateArgs,      # pydantic
      hosts={"etendo-classic"},
  ),
  "ui.draw_svg": UIToolSpec(… hosts={"etendo-classic", "widget"} …),
}
```

The description is the prompt. It is the only thing that makes the LLM pick the right
tool, so it is versioned code, not a database free-text field.

## 7. Security

| Risk | Mitigation |
|---|---|
| **SVG XSS** — the LLM emits `<svg onload=…>`, `<script>`, `<foreignObject>` with HTML, `javascript:` hrefs, external `<image>`/`<use>` | Sanitise on the client with DOMPurify (`USE_PROFILES: {svg:true, svgFilters:true}`), plus a coarse server-side pre-check. Render inline (not `srcdoc`, not `<img src=data:>`), strip all event handlers and external references, cap bytes and node count, show a notice when anything was removed |
| **Prompt-injection driven navigation** — record content tells the model to open a window | (a) navigation requires an explicit user click by default; (b) window access is re-checked in Java against the real `OBContext` role (P4.3); (c) navigation is read-only — no capability may *write* data in v1 |
| **Client claims a capability it was not granted** | The two-key rule (§3.1): the intersection is computed in Java from `ETCOP_APP_TOOL` |
| **Action replay** | `id` is an idempotency key; the dispatcher keeps a per-conversation set of executed ids |
| **Data leaking through `ui_context`** | Only ids/identifiers, capped at 4 KB, capped at 20 selected records |
| **`postMessage` origin** | Explicit target origin on send, `event.origin` check on receipt (issue S1) |

**Explicit non-goals for v1:** no UI tool may create, update or delete data, submit a form,
click a process button, or read fields the user cannot already see. Those need a separate
design with server-side authorisation per action, not a client dispatcher.

**Front-end**

- sanitiser: the hostile SVG corpus renders inert
- navigate handler: absent `window.parent.OB` degrades to a disabled card, no exception

**Manual**
- Classic → toolbar button → "open the Business Partner window" → card → click → opens
- widget host (no navigate capability) → the model must not offer navigation

## 9. Open questions for the team

1. **Auto-navigate or confirm?** The plan defaults to confirm. Auto is nicer in demos and
   worse in production; if auto is wanted it should be a per-user preference, not a default.
2. **Should UI tools be visible in `ETCOP_TOOL` at all?** The alternative is a pure code
   registry with no AD rows — simpler, but then a functional admin cannot decide which
   assistant may drive the UI. The plan chooses AD visibility.
3. **Where does the window catalogue come from?** The plan resolves names through a webhook
   at tool-call time (one extra HTTP hop, always fresh, permission-aware). The alternative —
   shipping the accessible-window list in `ui_context` — costs 10–20 KB per request and is
   impossible before P5.1.
4. **Does `ui.draw_svg` belong in the transcript or in a side panel?** Transcript in v1.
5. **P5.1 sequencing.** Moving off `EventSourcePolyfill` is the single highest-value fix in
   this whole document, and it is independent of UI tools. If there is appetite, do it
   *first* and the 4 KB cap in P1 disappears.

## 11. WebMCP as the discovery mechanism (added 2026-09-03)

A parallel effort on `epic/ETP-3504` registered four WebMCP tools in Etendo Classic
(`modules_core/com.etendoerp.client.application/web/.../webmcp-navigation.js`):
`etendo_list_windows`, `etendo_open_window`, `etendo_list_open_tabs`, `etendo_focus_tab`.
They are read-only plus navigation, and the menu they expose is already filtered by role because
it comes from `MenuManager`.

This replaces the hand-rolled `ui_capabilities` manifest of §4.1 with a standard discovery
mechanism, and it makes §9.3 moot: the window catalogue is never shipped in the context — the
LLM calls `etendo_list_windows` with a `query` at tool-call time. Four small tool descriptors
travel instead of 240 menu entries.

### Verified browser API facts

Measured against Chrome 152 with `chrome://flags/#enable-webmcp-testing`, **from inside the chat
iframe's own realm** (`web/com.etendoerp.copilot.dist/`), not from the parent:

- The namespace is `document.modelContext`, **not** `navigator.modelContext` (deprecated in
  Chrome 150).
- **The iframe sees the parent's tools through its own `document.modelContext`.** WebMCP scopes
  tools by origin, not by document, so a same-origin iframe inherits them. `window.parent` is
  unnecessary — using the iframe's own context avoids coupling the chat to the host page.
- `tool.inputSchema` arrives as a **JSON string, not an object** — `JSON.parse` it before turning
  it into a tool definition for the model. Consistent with the rest of the API: `executeTool`
  takes its arguments as a JSON string and returns its result as a JSON string.
- `executeTool(tool, args)` takes the **`RegisteredTool` object**, not the tool name.
- `registerTool` is asynchronous; deregistration is by aborting an `AbortSignal` passed in the
  second parameter. There is no `unregisterTool`. Registering a duplicate name rejects with
  `InvalidStateError`.
- `RegisteredTool.window` identifies the registering realm — useful to tell tools registered by
  Classic from any the chat itself may register later, without name heuristics.
- `ontoolchange` is available in the iframe, so a cached descriptor set can be invalidated
  reactively instead of by polling.
- Requires a secure context. Origin trial runs through Chrome 156.

Executing `etendo_open_window({windowId: '184'})` from inside the iframe opened the window as a
SmartClient tab in the parent. **The bridge works end to end with no backend involvement.**

### What this does not solve

The three blockers of the Java path stand, and they are ordered:

1. **The Java engine has no tool loop.** `CopilotEngineSelector.unsupportedReason` deliberately
   routes any agent declaring tools to Python. Until F5 of the LangChain4j plan exists, WebMCP
   buys nothing on the Java engine. This is the critical path.
2. **The forward channel cannot carry tool definitions or results.** The GET whitelist is four
   parameters wide, and with the client re-invocation loop below the *tool result* also travels
   back in the request — `etendo_list_windows` unfiltered returns 50 entries with full paths,
   several KB. This makes the POST migration (P5.1) a prerequisite rather than a nice-to-have.
3. **A tool call needs a mid-request round trip.** Chosen approach: the server emits a
   `tool_call` frame and ends the request; the client executes it and re-invokes the endpoint
   with the result; the server rebuilds history plus result and continues. This fits the existing
   stateless design because the conversation memory already lives in `ETCOP_MESSAGE`, not in the
   runtime. No WebSocket.

Security conclusion is unchanged and worth restating: the tool runs in the browser under the
user's own session, so it inherits the user's permissions — which is precisely why prompt
injection matters more than authorization here. An argument dictated by record content executes
with the user's rights. Confirm-by-click for anything that mutates, plus the `OBContext`
re-check for navigation.
