# Java replacement design: MCP client and server

## Summary

MCP is two separate integration surfaces and should stay separate in the Java engine: an outbound client that turns per-agent `mcp_servers` into LangChain4j `ServerTools`, and an inbound servlet that serves an agent by ID to external MCP clients. The Python client opens a new `MultiServerMCPClient` per request, retrieves tools under a 45-second discovery timeout, then the hand-written Java tool loop can consume those tools through `ToolSpecification`/`ToolExecutionRequest` (the engine already uses the manual loop per the parity plan). For transport, use LangChain4j MCP client for remote servers; support only transports expressible by its APIs and reject/record unsupported config rather than silently dropping it. The inbound server is not provided by `langchain4j-mcp`; implement MCP JSON-RPC/Streamable HTTP in a Copilot-owned servlet, reusing servlet container routing and Copilot Java services, not GO classes.

The Python server has two modes: standard exposes an agent-specific `ask_agent_<name>` tool; direct exposes `get_agent_prompt` plus agent tools (and for supervisor agents, team-member ask tools). It authenticates Etendo SWS bearer tokens, has legacy token header/query alternatives, OAuth 2.1 discovery/login endpoints, and dynamically starts one local Uvicorn server per identifier behind a proxy. Replace dynamic ports/proxy with a single servlet endpoint and keyed, bounded instance/config cache; preserve URL patterns and returned tool contracts. No MCP resources are currently registered by the inspected `resources/` package (only base resource scaffolding), and session tools intentionally register nothing.

## Scope decisions

- The Copilot module MUST NOT depend on `com.etendoerp.go`. GO is design reference only. Reimplement the small required transport/auth/session/context concepts under `com.etendoerp.copilot`.
- For direct tools, invoke Java engine/tool registry services in-process and execute under the asking user's captured `OBContext`; do not invoke an LLM from a separate Python process. The Python behavior's ask-agent endpoint does loopback `/sws/copilot/question`, but in-process replacement may call the same Java engine service directly, preserving conversation ID and identity semantics. If parity constraints require public endpoint semantics, make that choice explicit.
- Keep the existing hand-written model tool loop (parity plan § decisions), adding MCP client tools alongside local tools rather than introducing AiServices.
- GO supports MCP 2026-07-28 stateless modern requests plus legacy initialize revisions 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25. Evidence: GO `McpProtocolVersion.java:20-52`. A Copilot servlet can initially target 2025-03-26 Streamable HTTP; pin a spec version in tests and document any deliberate gap. Supporting modern 2026-07-28 would require the request-era/header behavior from GO; do not claim compatibility until implemented.

## A. Outbound MCP client

### Existing contract and request representation

`AssistantSchema.mcp_servers` is an optional list of free-form dicts (`modules/com.etendoerp.copilot/copilot/core/schemas.py:51`). `convert_mcp_servers_config` makes a map keyed by `name` (fallback `server_N`), drops disabled entries, removes `name`, defaults missing `transport` to `stdio` (`copilot/core/agent/multimodel_agent.py:43-71`). `get_mcp_tools` constructs a fresh `MultiServerMCPClient` per request and calls `get_tools()` under `asyncio.wait_for(..., timeout=45.0)` (`:153-172`). It repairs missing JSON schema `properties` and array `items` (`:74-149`) and returns no tools on discovery failure (`:164-183`, remaining function should be preserved semantically; graceful failure currently hides source failures).

Java request contract: pass the exact server list in the agent request, preserving each object's `name`, `disabled`, `transport`, endpoint/command/args/env/headers/auth fields. Normalize only at the client boundary into a `Map<String, McpServerConfig>`; skip disabled entries and default transport only if Python's default is retained. Do not infer transport from URL. For the Java engine response/request schema this remains the existing `mcp_servers` JSON field.

### LangChain4j adapter design

Add `implementation("dev.langchain4j:langchain4j-mcp:${langchain4jVersion}")` to the worktree `build.gradle` (existing 1.19.0 version and core/provider deps at `build.gradle:12-13,84-90`). Client API classes to investigate/use from the 1.19.0 artifact: `McpClient`, `McpTransport`, `McpToolProvider`, `McpToolProvider`'s tool retrieval/provider adapter and `McpClient.Builder`; likely transports `HttpMcpTransport` (Streamable HTTP) and `StdioMcpTransport` [INFERENCE: artifact API signatures not checked from dependency sources]. LangChain4j's normal tool bridge is `dev.langchain4j.agent.tool.ToolSpecification` / `ToolExecutionRequest`, with `dev.langchain4j.service.tool.ToolProvider` / `ToolProviderResult` potentially available; choose the adapter that fits the current manual loop. Do not add `langchain4j-mcp-spring-boot-starter`: the module is servlet/CDI/Etendo-managed and needs explicit lifecycle/context handling.

Build a `McpClientToolLoader` interface such as `List<ExecutableTool> load(List<McpServerConfig>, Duration discoveryTimeout, ToolExecutionContext context)`. The adapter connects clients, lists tools, maps each remote tool to `ToolSpecification` with JSON schema from the MCP `inputSchema`, and retains a dispatcher keyed by unique internal ID. On tool execution, call the corresponding MCP client's `callTool(name, args)` and normalize `CallToolResult` text/image/structured content and `isError` into the engine result envelope. Keep external name stable when unique; for collisions qualify by server name (e.g. `server__tool`) and keep a reverse map; never rely on ad hoc string parsing. Python naming details are not available from this inspection [INFERENCE]; exact duplicate-name behavior needs a contract test. Reconnect/close per request or use bounded reusable clients with explicit close; Python creates per-request clients, so per-run lifetime is safest for parity. Enforce discovery timeout 45s, plus a configurable bounded tool-call timeout [INFERENCE: Python adapter's tool-call timeout not inspected].

Transport/config mapping:

| MCP server JSON fields | Java mapping | Notes |
|---|---|---|
| `transport: "stdio"`, `command`, `args`, `env` | `StdioMcpTransport` process parameters | Python defaults stdio. Security risk: agent config can start arbitrary local processes; restrict through explicit allowlist/policy or disable stdio in hosted runtime. |
| `transport: "http"`/`"streamable_http"`, `url`, `headers` | Streamable HTTP transport with headers | Preserve configured Authorization/custom headers. Do not log secret values. |
| `transport: "sse"`, `url`, `headers` | legacy SSE transport only if LC4j 1.19.0 supports it; else unsupported configuration error | [INFERENCE] Exact supported transports depend on artifact API. Don't silently downgrade SSE/HTTP. |
| Python `MultiServerMCPClient`-specific auth/options | map recognized fields explicitly; reject unsupported auth modes | Preserve OAuth/token refresh only if implementation is available; no fabricated support. |

Security: external remote MCPs can leak prompts/data; honor per-agent allowlists and avoid forwarding Etendo user's bearer by default. Tool calls should use the server's configured credential only; provide user token passthrough solely as explicit config. Tool execution remains on user's request context where needed; no admin context. Never place bearer credentials in tool names/descriptions/logs.

## B. Inbound dynamic MCP server servlet

### Python behaviors to preserve

- Startup: `run.py:52-53` calls `start_simplified_dynamic_mcp_with_cleanup`; manager launches a dedicated daemon thread/event loop (`copilot/core/mcp/simplified_dynamic_manager.py:22-89`). `COPILOT_PORT_MCP` / `copilot.port.mcp` default is inconsistent in docs/env but runtime config uses 5006 (`manager.py:70-77`, `config.gradle:69-78`); module README documents 5007 (`README.md:143-160`). Java should use Etendo's `copilot.port.mcp` only if still hosting separately; a servlet mapping needs no own port. Compose/Docker exposes MCP port (`compose/com.etendoerp.copilot.yml:8-12`; `tasks.gradle:488-520`).
- Routes are `/{identifier}/mcp` (standard) and `/{identifier}/direct/mcp` (direct), methods GET/POST/OPTIONS (`simplified_dynamic_server.py:500-511`). Path identifier validation allows alphanumeric, underscore, hyphen (`:520-527`). Python dynamically creates isolated instance and agent config on first use (`:535-578` vicinity); proxy creates local server on an allocated port, forwards MCP traffic, handles failure/restart, and expires inactive instances (`:366-450, 560-721`). Java should remove per-instance listener ports and proxy entirely: servlet path is mapped in the existing Copilot/SWS namespace and each request dispatches using `{identifier}`.
- Authentication extracts `etendo-token`, `Authorization: Bearer`, `x-etendo-token`, then query `token` (`auth_utils.py:18-55`); no credential returns 401 and `WWW-Authenticate` referencing protected-resource metadata (`simplified_dynamic_server.py:525-545`). It then stores normalized token in thread context. `CopilotAuthProvider.verify_token` authorizes token against `GET /sws/copilot/assistants`, requiring an `app_id` matching this identifier, with 15-second timeout (`auth_provider.py:27-107`). Do not cache token auth globally across agents: Python's cache keys token only, a cross-agent authorization flaw; Java should cache token+agent with expiry or revalidate. Internal servlet can validate SWS JWT locally with Copilot's own auth APIs; invoke authorization policy for app ID and user role. No GO auth types.
- Standard mode's ask-agent tool calls `/sws/copilot/question` with `{question, app_id, conversation_id?}`, forwarding request bearer token, timeout 300s (`agent_tools.py:726-802`). Direct mode uses `ToolLoader.get_all_tools(agent_configuration, enabled_tools, include_kb_tool=true, include_openapi_tools=true)`, converts tools to FastMCP tools, and adds `get_agent_prompt` (`agent_tools.py:600-640`; `_gen_prompt_tool` follows). Direct supervisor mode exposes team-member ask tools instead of supervisor tools (`:610-620`). Standard registers `ask_agent_<sanitized name>` if agent config exists (`simplified_dynamic_server.py:116-145`); avoid duplicate logic by shared registry.
- Tool conversion uses LangChain BaseTool name/description/schema and `ainvoke`, preserves schema as JSON, and currently creates a dummy error tool on conversion failure (`agent_tools.py:386-453`). Java should expose the same available registry tools and schemas, but fail instance setup clearly rather than registering a dummy success-shaped tool.
- Prompt tool returns agent structure/config; MCP resources package is only skeleton (`copilot/core/mcp/resources/base.py`, `__init__.py`), basic tools provide identifier/context utilities (`tools/basic_tools.py:1-44`), and `session_tools.py:12-23` explicitly registers no session tools. No resource or prompt registrations were found beyond prompt-as-tool. Health/instance introspection routes exist at `/`, `/health`, `/instances` (`simplified_dynamic_server.py:440-498`); decide if needed externally, and don't expose internal instance/token details without auth.
- Python OAuth provider implements OAuth 2.1 + PKCE, dynamic client registration, auth code/pending state/token in memory, Etendo login UI, and access token IS Etendo JWT; auth code and pending TTL 5m, token cache TTL 24h (`oauth_provider.py:1-104`). OAuth routes include well-known metadata, authorize/token/register/revoke and login (`simplified_dynamic_server.py:460-498`). This is materially different from raw SWS token header; preserve only if customer-configured `auth_type: oauth` is supported in GetMCPConfiguration. Replace with servlet-safe OAuth handlers or use Etendo's existing login/token utilities; do not copy GO OAuth classes.

### Java configuration / external clients

`CopilotUtils` adds configured `mcp_servers` to agent request (`src/com/etendoerp/copilot/util/CopilotUtils.java:1128-1132`). `MCPUtils.getMCPConfigurations` reads active `CopilotAppMCP` to active `CopilotMCP`, performs variable substitution, normalizes object/array config and fills name (`src/com/etendoerp/copilot/util/MCPUtils.java:41-82`). `GetMCPConfiguration` mints a SWS token (`src/com/etendoerp/copilot/process/GetMCPConfiguration.java:126-132`), emits URL `/{agentId}/mcp` or `/direct/mcp` (`:570-590`), and supports `oauth`, `token_header` (default), `token_url`; token header embeds `Authorization: Bearer ...` while token_url puts token in query string (`:620-640`). It supports remote mode via `npx mcp-remote` (`:610-639`). The Java servlet should retain those URLs and standard config keys; token_url is a credential-in-URL risk and should stay only for strict legacy compatibility, with redacted access logs. Do not require Python/Docker sidecars for in-process operation. Docker build/compose port/environment logic becomes obsolete only when no Python runtime still uses it; see `tasks.gradle:488-520`, Compose port mapping and README. Keep deployment config only if the Java servlet is served through external container port; normal servlet deployment uses Etendo's port.

### GO design reference: concepts to reimplement, not imports

GO `McpServlet` is a POST JSON-RPC 2.0 servlet using synchronous Streamable HTTP because Etendo servlet filters do not support async SSE (`modules/com.etendoerp.go/src/com/etendoerp/go/mcp/McpServlet.java:61-72,147-150`). It authenticates inline, applies CORS, dispatches methods, handles no-ID notifications as 202, and exposes protected-resource metadata while rejecting GET SSE (`:147-240,560-606`). GO's version table and request negotiation are in `McpProtocolVersion.java:20-52`. Its method/tool dispatcher is `McpToolRouter.route(toolName,args,scopes)` (`McpToolRouter.java:120-163`), and registry is `ToolRegistry.java` [INFERENCE: registry internals not opened]. `McpSessionManager.executeInContext` restores previous OBContext in finally, resolves effective client/org, flushes success, rollback-closes error (`McpSessionManager.java:29-123`).

Implement in Copilot-owned package:
1. `CopilotMcpServlet`: path `/sws/copilot/mcp/*`; GET protected-resource metadata and optional OAuth discovery, OPTIONS CORS, POST bounded JSON-RPC. Streamable HTTP stateless POST response; no async/SSE. Handle initialize/capabilities/tools/list/tools/call/ping (where version requires), notification 202, JSON-RPC errors and HTTP status rules. Request/response content type, `MCP-Protocol-Version` and session header behavior must be explicit.
2. `McpAgentResolver`/`McpAgentInstance`: resolve external ID to accessible active agent, build mode-specific registry and metadata, bounded cache keyed at least by agent ID+mode (and never a principal's credential), invalidate or TTL. Since Etendo DB/config can change, define cache invalidation. Servlet doesn't create ports or proxy.
3. `CopilotMcpToolRegistry` and `CopilotMcpToolRouter`: immutable tool descriptions and schema, call dispatch to Java tool registry or question-service. Reimplement only JSON-RPC/MCP glue; reuse Copilot's own agent/tool services.
4. `CopilotMcpAuthenticator`: accept SWS token via Authorization header; legacy `etendo-token`/`x-etendo-token` and query token only if compatibility required. Validate cryptographically / via existing SWS helpers and authorize agent membership as asking user; bind identity and role. Never admin mode. Add RFC 9728 `/.well-known/oauth-protected-resource` metadata and `WWW-Authenticate` challenge. For OAuth client config, add OAuth discovery/PKCE only if required by existing configured clients; Java external servlet must return the same Etendo SWS JWT token after successful login.
5. `McpToolExecutionContext`: capture identity on servlet request thread and wrap every tool invocation, restore prior context in `finally`, flush/rollback per policy. Follow GO lifecycle lesson but derive context via Copilot/SWS/core APIs; no `com.etendoerp.go` imports. Since this is same thread on synchronous servlet, no implicit thread propagation; if tool/model executor switches thread, capture/install identity explicitly.

### Duplication and future shared interface

Duplicated small concepts: JSON-RPC and MCP HTTP framing/negotiation; auth token extraction/challenge and protected-resource metadata; request-scoped OBContext execution/cleanup; tool definition and dispatch contract; perhaps OAuth PKCE/login state. Do NOT duplicate GO's Neo tool catalog, schema-forge access, OAuth scope taxonomy, GO session/cookie authenticator, telemetry, business tool handlers, nor GO dependencies. A later shared-library seam could be a tiny neutral interface `McpToolProvider { List<McpToolDefinition> listTools(Principal); McpCallResult callTool(Principal, String, JsonNode); }` plus `RequestIdentity` and `ContextExecutor<T>`. However JSON-RPC servlet, authentication and Etendo context lifecycle are product-specific and should not be abstracted until both modules need the same contract; a shared dependency now violates boundary and increases coordination.

## Risks / open verification

- LangChain4j 1.19.0 MCP API names/signatures and SSE support were not inspected from source/Javadocs; **[INFERENCE]** above. Read the resolved artifact before coding and align with actual API.
- Existing Java engine has known Jackson 2.22-vs-2.13 runtime classpath conflict documented in `build.gradle:69-82`; MCP dependency may worsen/transitively constrain it.
- Current Python auth cache is token-only across agent identifiers; do not replicate this authorization bug.
- Python direct-mode tool conversion includes OpenAPI and KB tools; parity requires Java implementations available in `ToolLoader`, not only basic tools.
- `GetMCPConfiguration` embeds bearer in token_url and optional npx remote args; logs/config sharing can expose long-lived SWS JWTs. Preserve compatibility cautiously, redact and prefer headers.
- Dynamic per-agent processes currently isolate modes and expire after inactivity. Servlet cache must avoid unbounded per-agent state, stale tool schemas, cross-user credentials, or lock contention. Tool descriptions can be shared by agent/config but identity-specific permissions must be checked per call.
- Python server endpoint standard ask tool does HTTP callback with 300s timeout. In-process call avoids token loopback but parity in streaming, conversation persistence, hooks, and authorization must be demonstrated.
- Servlet mapping and servlet filters must be identified in module `AD_MODEL_OBJECT` / mappings and deployment descriptor before implementation [INFERENCE: exact mapping not located in this investigation].
