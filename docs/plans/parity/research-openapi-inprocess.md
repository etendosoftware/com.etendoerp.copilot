# OpenAPI/FLOW tools: in-process execution research

## Summary and answers

1. A Copilot `FLOW` file is an attachment-backed OpenAPI document generated by Etendo OpenAPI's `OpenAPIController` for a named `OpenApiFlow`; it describes operations, URL server, parameters, request bodies, and responses. `OpenAPISpecFlowFile` invokes `getOpenAPIJson(null, flow.getName(), host, true)`, adds the `ETENDO_TOKEN` instruction, and stores the JSON as a file attachment. At request assembly, specs are sent as `{name,type,spec}`. The Python generator turns each GET/POST/PUT/DELETE operation into a tool. For RX Headless datasource routes the path prefix is `/sws/com.etendoerp.etendorx.datasource`; actual suffixes and supported operations come from each flow's OpenAPI JSON and cannot be enumerated universally without a concrete flow spec. **The source tree did not expose an ETCOP_OPENAPI_FLOW record's generated JSON/referencedata fixture**, so do not assume all specs use the datasource routes.
2. RX's Java endpoint is `com.etendoerp.etendorx.services.DataSourceServlet` registered as the `datasource` `WebService`. It adapts requests to core `org.openbravo.service.datasource.DataSourceServlet`; reads dispatch internal `doPost` and writes to internal `doPost`/`doPut` after form/callout processing. Both facades currently require servlet request/response wrappers and an Etendo request/session context; their primary methods are not directly callable with only JSON/map arguments. Core `DefaultJsonDataService` is directly callable with parameter maps and JSON strings, but bypassing RX loses RX-specific projections, window/tab checks, form initialization, callouts, and response adaptation.
3. Outside GO, core's `DefaultJsonDataService` and SMF Secure Web Services' `SecureJsonDataService` are available in source. Both expose fetch/add/update/remove using `Map<String,String>` plus JSON text. Secure service's REST `OBRestServlet` maps `GET/POST/PUT/DELETE` to them and maps RSQL route/query into entity/id parameters. But that servlet explicitly wraps GET in admin mode, while the service itself has inconsistent context behavior (update sets cross-org-reference admin mode); neither is a safe drop-in equivalent to RX under Copilot's caller `OBContext` without auditing/fixing security semantics. The datasource core path has tab-aware permission checks when invoked through `DefaultDataSourceService`.
4. Recommended: generate one Java `ServerTool` per spec operation (or a single generic dispatcher with immutable operation descriptors), not dynamic compiled classes. Map only supported entity CRUD/read operations into a policy-enforcing in-process adapter around core JSON data service or datasource service, using the caller's non-admin context, resolving entity and authorization server-side, applying explicit projections, paging, and RX-compatible error shape. Keep operations needing RX-specific form/callout/projection/selector behavior, arbitrary non-entity HTTP resources, binary/download routes, or semantics not represented by core service on loopback through EtendoHttp. Do not silently change an operation's target service.

## 1. Spec content, operation generation, HTTP calls

- `OpenAPISpecFlowFile.exec` reads the file's `OpenAPIFlow` relation, gets/generated JSON from `OpenAPIController.getOpenAPIJson(null, flow.getName(), getEtendoHostDocker(), true)`, adds auth instructions, and writes the result for attachment processing. A blank filename becomes `<flow-name>OpenAPISpec.json`. `typeCheck` matches `FLOW`. The hook does not itself make a CRUD contract; the flow JSON is authoritative.
- Copilot request building adds app source entries with behaviour `spec` to a JSON array, each with `name`, `type`, and full `spec` content. The Python generator reads `servers[0].url`, iterates paths and only GET/POST/PUT/DELETE operations, derives tool args from operation parameters/requestBody, and invokes `do_request` with method/url/path/body/path params/query params/token.
- Route prefix constant: `/sws/com.etendoerp.etendorx.datasource`. For GET under this prefix, `_startRow` and `_endRow` are exposed as `startRow` and `endRow` tool args, remapped to original underscore parameter names for HTTP; other underscore-prefixed params are omitted. GET `q` receives RSQL operator guidance. POST/PUT JSON object request schemas become Pydantic body models; for datasource POST/PUT only explicitly supplied values are serialized (`exclude_unset=True`). POST supports oneOf and arrays; PUT only standard object schema. No DELETE body model is created by this generator.
- `do_request`: GET uses `requests.get(url+path, headers, params=query_params)`; POST/PUT use `application/json; charset=utf-8`, JSON UTF-8 body, and query params. Path template values are substituted. Unsupported method raises. Result is `{status_code,content}` (or binary-decoding fallback metadata), not parsed response JSON. Query args with None are removed. For same-host Etendo URLs, generator omits caller token field and sets special token marker `ETENDO_TOKEN`; `api_tool_util.token_not_none` retrieves user token and puts it in `Authorization` via `normalize_etendo_token`. For other URLs, optional token tool arg is used; SWS calls at Etendo host automatically fetch token if absent. Hook documentation explicitly says literal marker gets replaced.
- Exact path suffixes, methods and schemas are per `OpenApiFlow` export (`paths`/`servers`) and are not statically fixed by generator. Thus answer for RX routes is the prefix plus flow-declared path, with GET/POST/PUT/DELETE allowed if declared. Typical entity operations may be GET `/{datasource}/{id?}` and POST/PUT `/{datasource}` based on adapter route shape, but this form is **[INFERENCE]**, not confirmed from a checked-in generated flow spec. The source scan found no exported ETCOP_OPENAPI_FLOW-generated OpenAPI JSON/reference-data fixture; no per-flow request/response field list can be truthfully supplied.

## 2. Endpoint implementation and in-process callability

- RX registration: `com.etendoerp.etendorx/config/com.etendoerp.etendorx-provider-config.xml:3-7` registers bean name `datasource`, class `com.etendoerp.etendorx.services.DataSourceServlet`.
- RX implementation: `com.etendoerp.etendorx/src/com/etendoerp/etendorx/services/DataSourceServlet.java:86-116` class and core datasource servlet lookup. `doGet(path,HttpServletRequest,HttpServletResponse)` starts admin mode for setup, initializes request/session defaults, parses datasource and ID, translates `q` RSQL into SmartClient criteria, supplies pagination defaults, resolves tab/window, wraps request/response, then calls core datasource servlet `doPost` (read fetch action). It restores prior context at exit (see `:120-214`).
- `doPost` and `doPut` call `upsertEntity` (`:338-340`, `:1262-1265`); the upsert workflow resolves OpenAPI resource and tab/window, builds an Etendo request wrapper and invokes internal datasource POST/PUT; the internal methods are request/response based. These routines also cover form initialization/change handlers/callouts, lock/transaction/error behavior (see `:380-590` and `:650-730`; signatures are at `:338` and `:1262`).
- Core source exists, not just a binary: `modules_core/org.openbravo.service.datasource/.../DataSourceServlet.java`; its mapped request dispatch invokes `DataSource` services. `DefaultDataSourceService` invokes core `DefaultJsonDataService` and tests tab-based permissions for add/update (`modules_core/org.openbravo.service.datasource/.../DefaultDataSourceService.java:80-102,190-242`). Core JSON implementation is source in `modules_core/org.openbravo.service.json/.../DefaultJsonDataService.java`.
- Direct callability: core `DefaultJsonDataService.fetch(Map)`, `fetch(Map,QueryResultWriter)`, `add(Map,String)`, `update(Map,String)`, `remove(Map)` are callable without an `HttpServletRequest`; they require request parameter map (`entityName`, usually id/query/filter/paging/selected properties) and JSON payload for writes. They rely on active Etendo DAL/OBContext and perform internal DAL conversion/query. Core `DataSourceServlet` and RX facade are not callable without HttpServletRequest/Response because their method signatures and context/session/form logic require wrappers; adapting them means reifying request parameters, session, request context, tab and response behavior rather than simply calling a method.
- Important security mismatch: RX `doGet` explicitly calls `OBContext.setAdminMode()` while filling session state, then its internal core request executes under that request context and facade restores it. `DefaultDataSourceService` fetch establishes readable-org mode, add does similarly and permission-checks tab, but update calls `OBContext.setAdminMode(true)` in the shown source. Calling underlying Json service directly avoids transport but not automatically reproducing route security/permissions.

## 3. Existing non-GO JSON service APIs

### `SecureJsonDataService`

`modules_core/com.smf.securewebservices/src/com/smf/securewebservices/service/SecureJsonDataService.java` implements `JsonDataService` (deprecated annotation at lines 74-75), singleton via Weld at 83-92.

- `fetch(Map<String,String>)` delegates to fetch with readable-org filtering default true (`:96-110`); query parameters include `entityName`, optional `id`, `startRow`, `endRow`, `q`/where/filter/sort, `select`/selected properties, display field, count flags, etc. Its implementation constructs query service, returns standard Openbravo RPC JSON `response` including data/startRow/endRow/totalRows (`:114-243`, continuation through `:280`). Stream alternative `fetch(Map, QueryResultWriter)` (`:300+`).
- `add(Map,String)` marks add then delegates to update (`:805-824`); `update(Map,String)` parses JSON object/array, converts with `SecureJsonToData`, supports `{data:{...}}`/array-shaped inputs and merges entity/id from parameters, pre/post hooks, persists and returns service JSON (`:814-950+`).
- `remove(Map)` requires entityName/id; result is JSON response data, commits via DAL; see `:743-790`.
- `OBRestServlet` provides an RSQL REST facade: `get(path, requestParams)` maps route entity/id + query params via `OBRestUtils`, calls Secure service fetch through stream writer, returns WSResult data array (`modules_core/com.smf.securewebservices/src/com/smf/securewebservices/rsql/OBRestServlet.java:34-56`); post and put call add/update on JSON body (`:60-95`); delete by route ID calls remove, or accepts body `{data:[ids...]}` for multi-delete (`:98-149`). This is a non-GO Java route, but is an RSQL CRUD API, not the RX datasource protocol.
- Caveat: shown `OBRestServlet.get` explicitly does `OBContext.setAdminMode(true)` around fetch (`:46-51`). `SecureJsonDataService.update` calls `OBContext.setCrossOrgReferenceAdminMode()` (`SecureJsonDataService.java:828`); service methods and extra actions have their own policies. It is not enough to call this service and declare non-admin security parity.

### `DefaultJsonDataService` and `DefaultDataSourceService`

- Core `DefaultJsonDataService` is directly callable with map/content signatures (same JSON REST-compatible family); its servlet `org.openbravo.service.json.JsonRestServlet` demonstrates calls at fetch/add/remove/update (`modules_core/org.openbravo.service.json/src/org/openbravo/service/json/JsonRestServlet.java:141-218`).
- `DefaultDataSourceService` wraps it with entity binding and request/action checks. Fetch calls JSON data service after `addFetchParameters`; remove binds `entityName`; add/update test access permissions if `tabId` provided (`modules_core/org.openbravo.service.datasource/src/org/openbravo/service/datasource/DefaultDataSourceService.java:80-102,190-242`). This better captures ordinary data-source service semantics than bare JSON service but still doesn't recreate RX's request preparation, projections, form logic, and OpenAPI conversion.
- Compatibility: generic entity CRUD/read can map cleanly to JsonDataService if desired parameter conventions and response conversion are explicitly implemented. FLOW schema projection / field allowlist parity is not proven by these APIs: spec defines request/response schema but service fetch accepts selected-properties; need resolve allowed fields against the operation's schema and current Etendo entity/role access, not accept arbitrary model-supplied projection. RX projection-specific metadata and forms/callouts are outside the generic JSON CRUD call.

## 4. Proposed design and ordered plan

1. **Inventory actual contracts first**: load each ETCOP_OPENAPI_FLOW-associated generated `spec` and enumerate server URL, path/method, OpenAPI operationId/schema, entity/datasource mapping, and RX-specific behavior. Validate against the controller generator and concrete RX route mapping. Store operation descriptors immutable; never infer entity names from arbitrary user arguments.
2. **Classify routability**: classify operations as (a) plain entity CRUD/read supported by core JSON service; (b) RX datasource operation needing field projection/selector/form/callout/window or session logic; (c) non-data / binary / external route. Only (a) can initially be safely in-process with existing APIs. Keep (b)/(c) using existing EtendoHttp loopback until an equivalent service-level API is proven. Do not silently fall back across semantics.
3. **Implement an operation-backed `ServerTool`**: build `ToolSpecification` from selected OpenAPI operation; CDI bean name must match tool name (`ServerToolRegistry` resolves CDI implementations by exact name). A single generic dispatcher can be reused behind per-operation tool metadata. Validate allowed arguments against operation schema; map path/query/body to typed immutable descriptor, not guessed method/path from model output.
4. **Authorization/context boundary**: execute in caller's existing non-admin `OBContext`; do not mint token, set admin mode, reset context to admin, or trust entity names supplied by model. Resolve entity/path/operation from descriptor; authorize entity and fields for caller role/client/org; enforce table/window/tab write permissions. If operation requires behavior only accessible through RX route's admin-session bridge, leave HTTP until an equivalent non-admin service exists.
5. **Read path**: construct JsonDataService parameters for entity/id, filters, sort, selected properties, and paging. Enforce spec response field projection and role-readable access as an intersection. Translate `startRow/endRow` to core's expected `startRow/endRow` (RX translates to `_startRow/_endRow` for SmartClient route); preserve count/total rows and stable pagination. Check RSQL vs RX's `OBRestUtils.criteriaFromRSQL` + SmartClient AdvancedCriteria mapping; direct service's query parameter interpretation is not automatically identical.
6. **Write path**: serialize only explicitly supplied fields; set entity/id from descriptor/path, not body overrides. Call add/update/remove as supported by exact operation; preserve arrays/batch behavior only where contracts support it. Preserve transaction and callout/form semantics or leave such operations over HTTP.
7. **Normalize errors/responses**: map DAL validation/security/not-found/constraint failures to equivalent status/error JSON and tool result shape; current Python tool returns HTTP status/content wrapper, while direct Java tools must decide whether to preserve that wrapper or return decoded content consistently. Do not leak exception/SQL detail. Reproduce RX `response:{data,...}` and error payloads where parity is claimed.
8. **Fallback boundary**: operations unsupported by in-process adapter use EtendoHttp to the original URL/path/method with caller-authenticated token. Explicitly identify and test fallback so only the targeted CRUD calls stop looping back; preserve other flows.
9. **Tests/rollout**: compare in-process and HTTP results under same non-admin user for get-by-id/list/filter/sort/projection/pagination/count/create/partial-update/delete; cover role/client/org denial, invalid entity/field, malformed JSON, validation errors, empty result, and RX-specific form/callout operation classification. Confirm transaction behavior and no commit/admin escalation.

### Parity gaps and calls that cannot presently be classified in-process

- RX read applies `q` RSQL conversion to SmartClient criteria, sets tab/window/csrf/session parameters, and invokes datasource endpoint as a GET-to-internal-POST adaptation. Direct JsonDataService does not run that RX adapter logic.
- RX write does payload transformations, input field mapping, form initialization/change processing/callouts, locking and response merging. Generic JSON service write can persist entities but cannot by itself claim these semantics.
- Datasource spec responses may be constrained by OpenAPI projections; generic `selectedProperties` and DataToJson conversion are not demonstrated to enforce operation-spec projection identically. Enforce explicit schema field allowlist in adapter.
- Per-flow endpoint categories are unknowable without reading the concrete flow's emitted OpenAPI JSON; hence no honest exact enumeration of methods/responses or a definitive list of in-process vs loopback operations can be stated for every configured spec. Use step 1 to produce that operation matrix.
