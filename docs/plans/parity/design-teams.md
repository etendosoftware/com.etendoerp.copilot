# Java teams / supervisor runtime design (ETP-5136)

## Summary and recommendation

Implement `langgraph` parity inside `com.etendoerp.copilot`, without a GO dependency, by representing each Python team member as an independently configured LangChain4j-backed member agent and implementing the supervisor as a bounded, explicit Java orchestration loop. Reuse the Java engine's model factory, message construction, tool execution abstractions, `OBContext` propagation, and response/SSE contract. Prefer a hand-written supervisor loop initially over LangChain4j's agentic module: this directly matches the existing decided hand-written tool loop (parity plan §Decisions), makes `TaskManagementTool` state and member dispatch explicit, and avoids tying parity to agentic module APIs before its fit is proven. `dev.langchain4j:langchain4j-agentic:1.19.0` is a possible alternative, but whether its 1.19.0 API supports the needed dynamic team/member and observable supervisor semantics is [INFERENCE]; confirm by dependency/API inspection before choosing it.

Java's present engine only supports plain `langchain`/`multimodel` chat payloads without server tools, KB, OpenAPI or MCP (parity inventory and `CopilotEngineSelector`). Its `LangChain4jEngine` takes request history, asks one `ChatModel` once, and emits one final SSE answer. Team requests (`langgraph`) require selector support and request mapping before graph parity is reachable.

## Java integration and UI contract

- Java engine is `src/com/etendoerp/copilot/engine/LangChain4jEngine.java:35-110,114-178`. It calls `ChatModelFactory`, prepares LangChain4j messages (`SystemMessage`, `UserMessage`, `AiMessage`), supports `ClientToolSupport`, and streams via `RestServiceUtil.sendEventToFront` as `data: {"answer": {...}}`. History replay only turns USER into `UserMessage` and ASSISTANT into `AiMessage`; empty/nonstandard roles, including errors, are skipped (`:145-178`).
- Existing engine dependency block: `build.gradle:12-13,86-90` pins `langchain4jVersion=1.19.0`, core and provider modules OpenAI, Anthropic, Gemini, Ollama. If agentic module is selected, add `implementation("dev.langchain4j:langchain4j-agentic:${langchain4jVersion}")`; it is not needed for the recommended custom supervisor. No GO dependency. Reuse current provider modules; add other coordinates only for actual parity gaps.
- REST passes `HttpServletResponse` for synchronous/SSE execution; `RestServiceUtil.serverSideEvents` relays data frames (`src/com/etendoerp/copilot/rest/RestServiceUtil.java:339-354`), while `processResponseAndTrack` handles the final response (`:680-688`). Team run should be integrated into `CopilotEngineSelector` and dispatch inside engine implementation, not a second HTTP service.
- Chat UI source is `com.etendoerp.copilot.chat/src/App.tsx`: role imports/constants `:20-23`; role emoji/presentation `:270-280`; transient node/tool replacement `:297-305`; debug suppressed `:432-436`; SSE processing `:533+`. `docs/frontend-chat.md` describes UI pipeline and constants. Existing `node`/`tool` roles already represent transient progress; `error` is known. Preserve frame shape exactly: `data: {"answer":{"response":"...","conversation_id":"...","role":"node|tool|debug|error"}}`. Keep one `node` bubble updating member activity; `tool` may similarly replace. Final response is role-less/bot. No UI change is needed if the current role handling accepts `debug`, `error`, `node`, and `tool` as documented; verify the role constants/switch during implementation. UI may need a small correction if `error` or debug role is not rendered/ignored consistently. No token deltas: current UI creates separate message frames, not token accumulation.

## Proposed Java architecture

1. **Request adaptation and eligibility.** Add graph/team request support to the Java engine selector. Parse the current `assistants`, `graph`, supervisor fields, history, tools, and member configuration. Existing serialized app type constants determine member mode. Keep unsupported cases explicit (especially OpenAI Assistant mode, missing provider/model data, unsupported member server tools until their Java tool implementation exists). Reuse the Java request builder and avoid querying GO.
2. **MemberAgentFactory.** Interface: `MemberAgent create(MemberSpec spec, RequestContext context)`. Build a LangChain4j `ChatModel` using `ChatModelFactory` from each member's provider/model/temperature and member system prompt; attach that member's server/client tools through the shared tool registry/loop. Preserve sanitized display name separate from stable ID. Each invocation receives supervisor instruction plus relevant task/current conversation context and returns `{memberId, text, tool events, usage}`. Keep member histories isolated, not shared mutable message lists.
3. **SupervisorRunner.** Interface: `TeamResult run(TeamRequest request, EventSink sink)`. Use an explicit loop: supervisor model chooses a member/tool or final response; dispatch selected member; append the member result to supervisor conversation; continue until final response or bounded iteration/deadline. Use LangChain4j `ChatModel`, `ChatRequest`, `AiMessage`, `UserMessage`, `SystemMessage`, `ToolSpecification` (already used by engine), and existing hand-written tool loop patterns. Expose members as server-side supervisor tools with one tool per stable member ID, or a common dispatch tool; tool callback invokes `MemberAgent` as current request user. Choosing function-tool dispatch preserves model-controlled delegation. The explicit implementation can implement a LangGraph-style transfer protocol and task manager without `langchain4j-agentic`. `langchain4j-agentic` alternative uses 1.19.0 agentic APIs (exact type names/API signatures not verified; [INFERENCE]); do not introduce until dependency docs/source confirm it supports dynamic members, custom state, and streamed event hooks.
4. **TeamState / task state.** Request-scoped state owns pending tasks, current task, completed tasks, supervisor/member message lists, iteration count, and stable IDs. Implement four TaskManagement operations with immutable/controlled transitions; state key is `(assistantId, conversationId, userId)` to prevent cross-user leakage. Keep task state in-memory only for a single request if parity tests show checkpoints aren't relied on between turns; otherwise persist under an explicit Java store. The Python checkpoint path is per assistant+conversation and SQLite saver; persisted state across turns is current behavior and likely parity requirement [INFERENCE]. Prefer a copilot-owned persistence interface with versioned serialized state and tenant/user scoping, not Python SQLite internals.
5. **Memory/history.** Continue treating `ETCOP_MESSAGE` `history` as authoritative conversation history for the supervisor, as plain Java engine does. Build system + historical user/assistant messages + current question in order. For team member calls, preserve per-agent checkpoint behavior by storing scoped member conversation history/checkpoint alongside team state; separate each member's messages and do not replay tool/node/debug/error progress as conversational content. Carry history only when appropriate to that member. Because current `processResponseAndTrack` stores final user/assistant messages, avoid writing intermediate events into chat history; they are UI progress, not dialogue. If persisted per-member history must survive request restarts, add repository interface and persistence tests.
6. **EventSink and SSE.** Add callback `onEvent(role, response, conversationId)` from supervisor/member/tool execution. Emit JSON answer frames with the existing wrapper and `RestServiceUtil.sendEventToFront(writer, frame, true)`, flush after each event. Send initial `{}` frame exactly as current Java engine does. Map orchestration transitions to short `node` text (e.g. “Supervisor is thinking…”, “Delegating to X…”, “X is thinking…”, “X is using tool …”, “Writing the answer…”); tool invocation emits `tool`; unexpected errors emit `error`; debug detail emits `debug` only when debug flag enabled. Send one final role-less response frame. Keep exceptions and thread/user context cleanup deterministic; worker/thread hops must propagate `OBContext` per parity plan risk. On synchronous `/question`, run same orchestration without intermediate SSE and return `{"answer": ...}`.
7. **Security / tools.** Member tool callbacks execute as asking user, not administrator. Reuse parity `ToolExecutionContext`; the supervisor itself must not gain broader authority than members. Tool state and model calls must not be static/global. Existing engine currently only handles browser-side tool exchange, so member tools need server-side implementations before selecting tool-capable members for Java.

## Ordered independently implementable work packages

**WP1 — Contract and selector boundary**: Add a Java `TeamRequest` adapter from existing graph/team JSON; map supervisor/member fields; mark unsupported modes/capabilities in selector. Interfaces: `TeamRequest`, `MemberSpec`, `TeamEngine`. Tests for simple member configurations, absent history/IDs, `openai-assistant` unsupported and no silent fallback in strict mode.

**WP2 — Stateless members**: Implement `MemberAgentFactory` and `MemberAgent` for `langchain` and `multimodel` using `ChatModelFactory`; test provider/model/prompt routing, member name isolation, distinct member histories, tool-free result. Do not add shared GO dependency.

**WP3 — Supervisor and TaskManagementTool**: Implement `SupervisorRunner`, `TeamState`, member dispatch, final answer detection, and `get_next/add_tasks/status/mark_done`. Add max-iteration safety based on existing parity config, meaningful no-task/empty task semantics, structured final output where supported. This is independently unit-testable with fake model/member ports (test doubles only in tests).

**WP4 — History/checkpoint persistence**: Add `TeamStateRepository`/`MemberMemoryRepository` contract and implement selected persistence strategy. Replay ETCOP_MESSAGE history to supervisor; persist per-agent state scoped to user/assistant/conversation. Include restart/resume and isolation tests. Decide whether SQLite compatibility is required before implementing format; no unverified checkpoint compatibility claims.

**WP5 — SSE/event integration**: Add `TeamEventSink` and adapt servlet response streaming to preserve initial handshake and frame envelope; emit all node/tool/debug/error/final events. Ensure async and sync error behavior and final response tracking match existing route behavior.

**WP6 — Enable supported Java team configurations**: Update engine selector only after WP1-5 capability gate; run full parity tests. OpenAI Assistant mode remains explicitly unsupported unless separately implemented. Add runtime logging identifying Java team execution and any fallback reason.

**WP7 — Chat UI compatibility**: Preserve known roles and transient replacement. Only change `App.tsx`/constants if tests/review expose missing role rendering. Ensure error surfaced visibly, debug ignored/logged, node/tool progress not stored as persistent assistant history. Rebuild committed dist when UI changes.

## Risks / decisions to settle

- **Context propagation:** `OBContext` is thread-bound; asynchronous LangChain4j callbacks can lose user identity or leak it. Capture/restore/clean on every tool invocation and any executor hop.
- **State durability:** LangGraph SQLite checkpointing provides durable thread state; Java's existing engine only replays tracked history. Team/member checkpoint parity requires an explicit persistence decision; in-memory-only would be a behavior reduction [INFERENCE].
- **Tool parity:** Python members load configured tools, KB, OpenAPI; Java current selector excludes server tools/KB/OpenAPI/MCP. Do not enable teams broadly until tool capability gate and coverage are complete.
- **OpenAI Assistant:** Python graph member explicitly rejects it; Java builder transmits ID. Preserve this observed behavior (explicit unsupported), rather than implementing an unrelated remote API silently.
- **Agentic library:** `langchain4j-agentic` coordinate is plausible at pinned version, but API availability/suitability is unverified here. Hand-written loop aligns with parity decision #5 and avoids an unnecessary dependency.
- **UI frame semantics:** Existing chat replaces consecutive transient roles; member-name activity should stay in `response` and `role=node`. A new role would require explicit UI handling and should be avoided.
- **Structured output:** Supervisor response schema is configured in Python. Keep structured final output response shape and test alongside normal text; existing parity plan notes a request-key mismatch (`structured_output_json_schema` vs `output_schema`).
- **Build/runtime dependency risk:** Existing build note flags LangChain4j 1.19.0 versus Etendo Jackson 2.13 classpath conflict (`build.gradle:70-74`). Adding agentic module does not remove that existing risk and may add transitive exposure.

## Test strategy

- Unit tests for request adaptation, eligibility, name-to-member mapping, per-member model config, supervisor dispatch, task-state transition table, max-iteration termination, structured output, and event mapping. Cover edge cases: no members, unknown member, malformed/empty member response, empty task queue, repeated task completion, missing conversation ID, member tool failure, model exception.
- Contract tests asserting each emitted frame parses as `{"answer":{"response":string,"conversation_id":...,"role":...}}`, initial empty frame remains, final response is role-less, and SSE event order reflects supervisor → member/tool → final. Test sync response wrapper too.
- Memory tests replay USER/ASSISTANT in order, skip error/progress/tool roles, persist and resume state, isolate two users sharing conversation IDs and two teams sharing user, and avoid duplicate question replay. Validate actual `TrackingUtil` history construction and processResponseAndTrack before finalizing exact ordering.
- Integration tests with stub model/member ports for deterministic delegation and task queue behavior; then provider-backed tests only where credentials/configuration are available. No test should require GO module imports or admin context.
- UI tests or focused manual contract check for node/tool transient replacement, `error` visibility, `debug` suppression, and final bot answer; rebuild committed `web/com.etendoerp.copilot.dist` if source changes.
